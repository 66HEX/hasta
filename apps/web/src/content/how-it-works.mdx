## How it works

Hasta uses a [Kalman filter](https://www.cs.cmu.edu/~motionplanning/papers/sbp_papers/kalman/welch_intro_kalman.pdf) with a constant-velocity motion model to estimate pointer position and velocity. The first two valid samples with distinct timestamps initialize the estimate. Later measurements update it using their elapsed time and the filter's estimate of uncertainty. The filter receives the accepted mouse sample stream, including coalesced events when available.

During steady motion, the filter lowers process noise so small position errors cause smaller velocity corrections. A large deviation, or several aligned deviations spanning at least 8 ms, restores responsiveness for turns and braking. The filter keeps that response for 32 ms while the estimate settles.

When samples arrive no more than 8 ms apart, an isolated measurement that disagrees strongly with the estimated motion receives less weight. For gaps above 8 ms and up to 40 ms, the filter also compares the new step with recently measured motion. Reversals and steps consistent with recent speed use ordinary weighting; an unusually large increase in speed can receive stronger suppression. Longer gaps use ordinary Kalman updates and clear the confirmation history.

Consecutive deviations in a similar direction restore normal weighting. This reduces the influence of brief spikes, but can delay recognition of genuine acceleration. Several faulty measurements can also support each other, so a stable forecast is not proof of user intent.

`KalmanPredictor` projects the estimated position forward to the current frame time, then extends a straight trajectory using the estimated velocity. Its `KalmanPrediction` result contains the start and end points of that trajectory. Each intersection rule uses its own `withinMs`; `horizonMs` sets the forecast for custom predicates. The forecast assumes constant velocity, so longer horizons and larger margins increase the chance of a match that the pointer never reaches.

Each target is an axis-aligned bounding box (AABB), measured with `getBoundingClientRect()` in viewport CSS pixels. Bounds are read before callbacks, at most once per active animation frame. Scroll and resize events request a frame; repeated measurements during active prediction also follow layout changes and transforms. Disconnected and zero-area elements are skipped. Clipping, rotation, transparency, and overlapping content can leave unpainted or obscured areas inside the box.

A broad-phase AABB overlap test selects possible targets. The narrow-phase intersection test uses the [slab method](https://www.pbr-book.org/4ed/Shapes/Basic_Shape_Interface#RayndashBoundsIntersections): it computes when the trajectory enters and leaves the target's horizontal and vertical ranges, then intersects those time intervals. The first entry within the forecast window gives the contact point and ETA. `marginPx` expands the target box before this test.

With `includeCurrent: true`, Hasta also checks current contact and the segments between fresh, unfiltered mouse samples since the previous frame. This is a swept point-versus-AABB test, a simple form of [continuous collision detection (CCD)](https://digitalrune.github.io/DigitalRune-Documentation/html/138fc8fe-c536-40e0-af6b-0fb7e8eb9623.htm): it checks for contact along the path between samples, rather than only at their endpoints. It catches fast passes through narrow targets even when both sample endpoints are outside, and reports these observed crossings with zero ETA. The target uses its latest measured box; its own movement between measurements is not swept. Movement the browser never reports cannot be reconstructed.

A forecast callback runs once per continuous match, after matching observations span any `stableForMs` delay. New starts require a new measurement timestamp, so animation frames alone cannot establish stability after the pointer stops. Another run requires a lost match and fresh evidence, and respects `once` and cooldown; an unresolved callback never overlaps with itself. For intersection rules, a lost speculative match can retain its active signal for up to 32 ms while the forecast still reaches a box expanded by an additional 6 px. Retention ends sooner if the estimated direction changes by more than 15 degrees or speed drops below 70% of the last matching estimate. This release margin cannot start a callback. Leaving observed contact, losing the forecast, target detachment, and controller pause/disconnection still cancel immediately. Custom predicates cancel on their first false result. Old movement expires after `maxSampleAgeMs`; a longer horizon does not extend freshness. Pointer cancellation, pressed mouse buttons, pointer lock, window blur, and a hidden document reset prediction.

**Prediction uses mouse input only.** Keep normal tap, hover, focus, and click behavior; use predictions for work that can be canceled or safely cached. The debug switch shows measured bounds and the predicted trajectory.
